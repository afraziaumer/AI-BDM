# Known Limitations

Current, honest limitations as of this handoff. Update an entry only when submitted code and test evidence prove the condition has changed — do not silently remove or soften an entry.

## RESOLVED — `wappalyzer==2.0.1` was not actually reproducible (discovered and fixed during this handoff)

The version pin `wappalyzer==2.0.1` in `requirements.txt` did **not** guarantee reproducible package contents. Confirmed live: a genuinely fresh `pip install -r requirements.txt` on 2026-08-06 installed a **different, incompatible build** under the exact same version string than what this development machine had installed (and had patched — see the entries below). That build has no `Wappalyzer.py` at all, a completely different internal module layout (`analyzers/`, `browser/`, `parsers/` instead of the old flat structure), and its `Wappalyzer` class exposes `analyze`/`analyze_many`/`close` instead of the `.latest()` classmethod `tech_stack.py`'s legacy engine depends on.

**Impact before the fix, confirmed live, not hypothetical**: `tech_stack.py`'s legacy detection engine (`_get_wappalyzer()`) raised `AttributeError: type object 'Wappalyzer' has no attribute 'latest'` on a fresh install — Stage 5 (tech-stack detection) did not work at all, regardless of the three encoding/regex patches below.

**Fix implemented (2026-08-06): vendoring.** `wappalyzer` is no longer pip-installed — it has been removed from `requirements.txt` entirely. A working, pre-patched copy of the package (all three patches below already applied) is committed directly into this repository at `vendor/wappalyzer/`, and `tech_stack.py` inserts `vendor/` at the front of `sys.path` at import time so `import wappalyzer` always resolves to the committed copy, never whatever PyPI happens to be serving that day. This makes the install fully reproducible regardless of future upstream PyPI changes. See `vendor/wappalyzer/README.md` for exactly what's vendored, why, and the procedure for updating the vendored copy in the future.

**Verified**: fresh venv, `pip install -r requirements.txt` (no `wappalyzer` package installed at all), full test suite (`pytest -q`) passes with zero manual post-install steps — including the 3 tests in `tests/unit/test_wappalyzer_patches.py` that previously failed on a fresh install. `scripts/patch_wappalyzer.py` is retained only as the one-time tool used to re-vendor a newer upstream release in the future, not as a required post-install step anymore.

| Area | Current disposition |
|---|---|
| Yelp / Trustpilot scraping | Bot-protection defeats even the premium (ScrapingBee) fetch tier's stealth mode. A production fix would require Yelp's official paid Places API — evaluated for cost, not implemented. |
| Dockwa (and similar JS-rendered review widgets) | Review text is populated client-side after page load; the scraper only sees the pre-render HTML shell, so extraction finds nothing even when the listing itself is correctly matched. Would need a JS-rendering fetch tier or a dedicated Apify actor for that specific platform. |
| Roman Urdu / code-switched review text | Statistical language detection (`langdetect`) cannot reliably distinguish Romanized Urdu from English, since it uses the same alphabet and often includes real English words — confirmed live: `"Sindh Balochistan ka idk k Kya criteria hota..."` detects as `"en"`. The review-relevance check can produce false flags on this kind of text. A real fix needs an LLM judgment call or multilingual sentence embeddings; neither is implemented. This is explicitly **not** required to be fixed as part of the non-LLM/current-system handoff. |
| ScrapingBee monthly quota | The development account's 1,000-call monthly quota has been exhausted multiple times during testing, silently degrading the premium fetch tier pipeline-wide (native-fetch-only) until the plan resets or is upgraded. This is a billing constraint, not a code defect — `_upload_with_retry`/premium-fetch error messages surface the exact `"Monthly API calls limit reached"` provider response when it happens. |
| Reddit official OAuth API | Abandoned after repeated recaptcha/redirect-URI friction during app registration. Apify's `trudax/reddit-scraper-lite` actor is the production path for Reddit mentions; the official API integration was never completed. |
| CRM-acronym fuzzy matching | `"customer relationship management"` does not fuzzy-match the literal token `"crm"` in the evidence-retrieval layer. Accepted, deliberate limitation — the project's design philosophy avoids hand-maintained synonym lists; each query's own keyword-expansion step (see `LLM_planner.py`) is expected to spell out realistic surface forms instead. |
| Third-party package patches (Wappalyzer, encoding/regex) | Three real bugs (BeautifulSoup parser, UTF-8 encoding, a broken Symfony fingerprint regex), all pre-applied to the committed copy at `vendor/wappalyzer/` — see the RESOLVED item above. No longer something a developer needs to apply by hand after install. |
| Network instability | DNS/network faults are treated as transient and retryable, never cached as a genuine no-result (see the transient-failure-vs-empty-result fix in `phase3/google_maps.py` and `phase3/review_harvester.py`). Real DNS instability was observed repeatedly on the development machine during this project's testing — unrelated to the codebase, but worth knowing if a "failure" doesn't reproduce on retry. |
| Cloudflare R2 sync | Implemented and tested against a real bucket (`storage_sync.py`) — whole-folder atomic sync, correct hierarchy preservation (a real Windows path-separator bug was found and fixed here), incremental skip via a per-domain manifest, and a `StorageProvider` abstraction so other backends can be added later. Optional — the pipeline runs identically with or without R2 credentials configured. |
| LLM dependency | The entire query-planning, routing-fallback, final-reasoning, clarification, and moderation layer is LLM-based (Groq). There is currently no non-LLM alternative implementation for any of these stages — see `docs/ARCHITECTURE.md` for exactly which stages require an LLM call and which run independently of one. |
| API wrapper (`api.py`) | Exposes only Steps 1–2 of the pipeline (`POST /api/v1/pipeline/run`, plus read-only, cursor-paginated `/api/v1/leads` endpoints). Steps 3–8 (routing, final reasoning, tech-stack detection, evidence retrieval, Maps enrichment, accuracy audit) are only reachable via the `main.py` CLI entry point today, not via this API. |
| Test suite | No automated test suite existed before this handoff pass. Now covers smoke (`tests/smoke/`), unit (`tests/unit/`), mocked-provider (`tests/mocked/`), and opt-in live-provider (`tests/integration/`, `pytest -m live`) layers — 62 offline/mocked tests plus 4 live tests, all passing. See `docs/HANDOFF_SUMMARY.md` for exact commands. |
| `robots.txt` disallow rules not enforced | The crawler fetches `robots.txt` only to discover `Sitemap:` locations for contact-page discovery (see `docs/ARCHITECTURE.md`'s Scraping declaration) — it does not parse or respect `Disallow:` directives before fetching a page. This is a real, current gap, not a deliberate design choice. A production hardening pass should add `urllib.robotparser` (or equivalent) enforcement before Stage 2 fetches any page. |
| Structured logging / correlation IDs | Logging is plain-text (`timestamp [LEVEL] message` via stdlib `logging`), one logger per module — no job/correlation ID, no per-stage/duration field, no JSON output. See `docs/RUNBOOK.md`'s Logging & observability section. Fine for CLI use; a Laravel-facing service wrapper would need to add its own correlation-ID layer, not assume one exists here. |
| No closed-business detection (`phase3/google_maps.py`) | A Google Maps match that's actually a permanently- or temporarily-closed listing is presented identically to an open one -- rating/category/phone are returned with no closed-status flag anywhere. Confirmed live (2026-08-12): a real Serper `/places` lookup for a well-known closed retail location (`Toys "R" Us`) returned `{title, address, latitude, longitude, category, website, cid}` -- no `businessStatus`/`closed`/equivalent field at all. This is a data-source gap, not a code bug: the underlying Serper Places response this project depends on does not expose closed-status, so there's nothing in the payload to read. A fix would require switching to Google's own Places API (which does expose `business_status`) for this specific signal. |
| Same-address disambiguation depends on phone/name corroboration (`phase3/google_maps.py`) | When multiple businesses share a physical address (a strip mall, a shared building), address-token overlap alone can no longer tell them apart (fixed 2026-08-12 — see `find_place()`'s `address+corroborated` tier): the known business's phone number or a full name-containment match is required to pick the right one among several co-located candidates. If NEITHER corroborates for any of them, the lookup correctly returns unmatched rather than guessing -- so a legitimately co-located business can go unmatched if Serper never returned its phone number and its name doesn't fully contain the known name. |
| No cross-process lock on `commit_domain()` (`storage.py`) | Real corruption bug found and fixed (2026-08-12, SEC-013): two commits of the SAME domain racing used to nest one inside the other instead of replacing it (`shutil.move()` into an already-existing directory). Fixed by renaming any prior copy out of the way atomically before moving the new one in, which eliminates the nesting failure mode and narrows the unsafe window to two back-to-back atomic renames -- but this codebase has no cross-PROCESS lock anywhere, so a residual (much smaller) race window still exists if the same domain is committed by two separate OS processes at nearly the same instant (multiple uvicorn `--workers`, or two overlapping CLI runs). Same-process concurrency (multiple asyncio jobs in one `api.py` process) is fully safe -- `commit_domain()` has no internal `await`, so it cannot be interleaved by other tasks in the same process. **Recommendation: run `api.py` with a single worker process** until/unless a real cross-process lock (e.g. a file lock) is added. |
| No global circuit breaker for provider-wide quota exhaustion (`phase3/google_maps.py` premium-scraper path, `phase1_pipeline.py`'s `PremiumScraper`) | `PREMIUM_CIRCUIT_BREAKER_THRESHOLD` (phase1_pipeline.py) opens a circuit breaker per DOMAIN after 2 consecutive premium-fetch failures for that domain, but there is no run-wide breaker: once a provider's quota is genuinely exhausted for the whole account, every NEW domain touched in the same run still pays its own 2-failure cost to independently discover the same already-known fact before its own circuit opens. Not a retry storm (quota-exceeded status codes like 402 are not in `_PROXY_TRANSIENT_STATUS`, so they are not retried per-request), but not maximally efficient either. A real fix would classify the specific "quota exceeded" provider response and open a single process-wide flag on first sight of it. |
| **Two genuinely different businesses sharing one domain get silently merged (`data_pipeline.to_business_level()`)** | **Real, currently UNFIXED defect** (not just missing data), found and reproduced live 2026-08-12 (professional QA suite, AI-BDM-278/279). `to_business_level()` groups crawled pages by `_domain` ONLY, with no `company_name` component in the grouping key. Reproduced directly: two pages on the same institutional domain ("Pier 25 Marina" and "Pier 30 Cafe", both on `hudsonriverpark.org`) collapse into ONE business record — the majority `company_name` wins, the other business disappears from the result set entirely, and their emails are UNIONED together onto the surviving record (`marina@hudsonriverpark.org \| cafe@hudsonriverpark.org` both attached to "Pier 25 Marina"). This is not an isolated bug: `phase1_pipeline.py`'s own discovery-dedup cache (`existing_by_domain`), `storage.py`'s per-domain folders, `phase3/store.py`'s per-domain review/Maps cache, and `rag/chunker.py`'s per-domain filtering all treat **registered domain as the sole business identity key** — the same assumption that produces this bug is load-bearing throughout the entire pipeline. A real fix is a genuine identity-model change (domain+name, or some other compound key, propagated through discovery dedup, storage paths, caching, Maps matching, and RAG filtering) — not a safely-scoped one-function patch, and NOT attempted as part of this QA pass. Until fixed: a query that legitimately discovers two distinct businesses sharing one shared/institutional website will silently lose one of them and cross-contaminate contact data on the other. |
| Third-party code / data licensing — not independently audited | This handoff did not perform a line-by-line license audit of every dependency in `requirements.txt` or the vendored `wappalyzer` fingerprint database (`vendor/wappalyzer/data/technologies.json`, originally sourced from the upstream Wappalyzer project). Flagging honestly rather than asserting a specific license with unverified confidence: whoever owns legal/compliance review for this handoff should confirm the license terms of the vendored technologies.json data and any other bundled third-party data files before commercial use, rather than relying on this document's silence as clearance. All paid external services used (Groq, Serper.dev, ScrapingBee, Apify, GitHub API, YouTube Data API) are accessed via their own official APIs under their own published Terms of Service — no scraping of those providers themselves. |
